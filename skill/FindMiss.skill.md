# FindMiss · v0.1 · 找遗漏 · 暴假设 · 对原文 · 不判对错

> **一句话**：Agent 说"搞定了"——你的要求它真的全做了吗？FindMiss 逐条比对你的原始要求和 Agent 的交付结果，找出遗漏的需求和未声明的隐藏假设。
>
> **三节点**：① 提（提取原始要求）→ ② 对（逐条比对交付）→ ③ 出结果（遗漏清单输出）。多一步就是多余。

---

## 触发条件

用户说 `/findmiss` `/fm` `查遗漏` `漏了什么` `miss 一下`。

**适合**：Agent 交付了结果（代码、方案、报告、回答），你想知道它有没有漏掉什么。
**不适合**：审 prompt 质量（那是 FindGap 的事）、审执行过程（那是 FindAction 的事）。

---

## 与 FindGap / FindAction 的分工

```
FindGap    事前    你的请求缺了什么（照输入）
FindAction 事中    Agent 做了什么  （照过程）
FindMiss   事后    结果漏了什么    （照输出）  ← 你在这里
```

FindMiss 只回答两个问题：
1. **你要求的，Agent 有没有全做到？**（遗漏检测）
2. **Agent 替你做了哪些你没说的决定？**（假设暴露）

不判断结果对不对、好不好。漏了就是漏了，假设了就是假设了。

---

## 内部检查引擎（6 条规则，不对外展示代号）

以下规则在内部驱动遗漏检查，但输出中**只用人话描述发现，不展示规则代号**。

| 内部代号 | 查什么 |
|---------|--------|
| M-REQ | 原始要求中的每条显式需求，在结果中是否有对应交付 |
| M-EDGE | 原始要求中提到的边界条件/异常场景，结果中是否覆盖 |
| M-CONSTRAINT | 原始要求中的约束条件（技术栈、性能、兼容性），结果中是否遵守 |
| M-ASSUME | Agent 在结果中做了哪些原始要求未提及的假设（默认值、默认范围、默认技术选型）|
| M-IMPLICIT | 领域内的隐含常识要求（如安全、错误处理、可访问性），结果中是否覆盖 |
| M-SCOPE | 结果是否包含了原始要求未要求的额外内容（过度交付），可能引入复杂度 |

### 规则边界

- M-REQ vs M-EDGE：REQ 查显式写出的需求，EDGE 查显式提到的异常/边界
- M-CONSTRAINT vs M-ASSUME：CONSTRAINT 查用户明确说的限制条件，ASSUME 查用户没说但 Agent 自作主张的
- M-IMPLICIT：只标注领域内公认的隐含要求，不凭空发明需求
- M-SCOPE：过度交付不标为错误，只标为"额外内容，请确认是否需要"

## 三节点执行流程

### 节点 ① 提（提取原始要求）

从用户的原始 prompt / 需求描述中提取结构化要求清单：

**提取维度**：

| 维度 | 提取内容 | 示例 |
|------|---------|------|
| 功能需求 | 用户明确要求做的事 | "添加用户登录功能" |
| 边界条件 | 用户提到的异常/极端情况 | "密码错误超过 3 次锁定" |
| 约束条件 | 用户指定的技术/性能/范围限制 | "用 JWT 鉴权""P99 < 200ms" |
| 交付格式 | 用户期望的输出形式 | "写测试""更新文档" |

**提取原则**：
- 只提取用户**明确写出**的要求，不推测"他可能还想要"
- 每条要求保留原文引用，供后续比对
- 如果用户的 prompt 很短（如"帮我改一下这个 bug"），则从上下文（对话历史、文件内容）补充推断，但标注为"从上下文推断"

### 节点 ② 对（逐条比对交付）

**步骤 2.1：要求 × 交付比对矩阵**

逐条检查每个要求在交付结果中是否有对应实现：

| 原始要求 | 交付中是否覆盖 | 状态 |
|---------|--------------|------|
| "添加用户登录功能" | 有 login 页面和 API | ✅ 已覆盖 |
| "密码错误超过 3 次锁定" | 未找到锁定逻辑 | ❌ 遗漏 |
| "用 JWT 鉴权" | 使用了 session-based auth | ⚠️ 偏离约束 |
| "写测试" | 未找到测试文件 | ❌ 遗漏 |

**步骤 2.2：隐藏假设扫描**

扫描 Agent 的交付结果，找出用户未提及但 Agent 自行决定的内容：

| Agent 的决定 | 用户是否提到 | 假设类型 |
|-------------|------------|---------|
| 使用 PostgreSQL 数据库 | 未提到 | 技术选型假设 |
| 密码最少 8 位 | 未提到 | 业务规则假设 |
| API 返回 JSON 格式 | 未提到 | 接口格式假设 |
| 默认时区 UTC | 未提到 | 环境假设 |

**步骤 2.3：隐含要求检查**

检查领域内公认的隐含要求是否被覆盖：

| 隐含要求 | 领域 | 交付中是否覆盖 |
|---------|------|--------------|
| 错误处理 | 通用 | 无 try/catch，无错误边界 |
| 输入校验 | 安全 | 无参数校验 |
| 日志记录 | 运维 | 无日志调用 |

**注意**：隐含要求检查只针对**该领域公认的必要项**，不凭空发明需求。标注为"领域惯例建议覆盖"而非"遗漏"。

### 节点 ③ 出结果（遗漏清单输出）

**输出模板**：

```
FindMiss · 比对 N 条要求，发现 M 处遗漏，K 个隐藏假设

---

❌ 遗漏 · {遗漏的需求名}

原始要求："{用户原文}"
交付状态：未找到对应实现
影响范围：{这个遗漏会导致什么}

---

❌ 遗漏 · {遗漏的需求名}

原始要求："{用户原文}"
交付状态：未找到对应实现
影响范围：{这个遗漏会导致什么}

---

⚠️ 偏离约束 · {偏离的约束名}

原始要求："{用户原文}"
实际交付：{Agent 实际做的}
偏离说明：{具体偏离了什么}

---

🔶 隐藏假设 · {假设名}

Agent 的决定：{Agent 自行决定的内容}
用户是否提到：未提到
影响：{这个假设可能带来什么影响}
建议：确认此假设是否符合你的预期

---

🔶 隐藏假设 · {假设名}

Agent 的决定：{Agent 自行决定的内容}
用户是否提到：未提到
影响：{这个假设可能带来什么影响}
建议：确认此假设是否符合你的预期

---

💡 领域惯例建议 · {建议名}

惯例要求：{该领域通常需要做的}
当前状态：交付中未包含
建议：{领域内的通行做法}

---

📊 要求覆盖度

| 要求 | 状态 |
|-----|------|
| {要求1} | ✅ 已覆盖 |
| {要求2} | ❌ 遗漏 |
| {要求3} | ⚠️ 偏离 |
| {要求4} | ✅ 已覆盖 |

覆盖 X/Y（Z%）
```

**输出规则**：
- ❌ 遗漏：必须有"原始要求"原文引用 + "影响范围"
- ⚠️ 偏离：必须有"原始要求"和"实际交付"的对比
- 🔶 隐藏假设：必须指出 Agent 替用户做了什么决定
- 💡 领域惯例：标为"建议"而非"遗漏"，不强加需求
- 不输出任何规则代号
- 不评判交付质量，只陈述覆盖事实

---

## 红线（4 条）

1. **只找遗漏和隐藏假设，不判对错**——做了但做错了不归这里管
2. **每条遗漏必须追溯到原始要求原文**——说不出出处的遗漏不输出
3. **隐藏假设必须指出 Agent 替你做了什么决定**——不含混地说"有些地方可能有假设"
4. **不替用户决定结果好不好**——只照出看不到的，让用户自己判断

---

## 杜绝（明确不做什么）

- ❌ 判断代码写得好不好（那是 code review）
- ❌ 判断 Agent 执行过程是否合规（那是 FindAction 的事）
- ❌ 判断 prompt 写得清不清楚（那是 FindGap 的事）
- ❌ 替用户决定是否接受交付结果
- ❌ 凭空发明用户没提的需求当作"遗漏"
- ❌ 运行时维护静态知识库
- ❌ 输出中展示规则代号
- ❌ 给评分或 PASS/FAIL
